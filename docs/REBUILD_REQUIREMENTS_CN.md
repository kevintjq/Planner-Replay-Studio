## 01. 项目背景与最终目标

目前软件发布的测试版本存在严重问题：

- 很多功能无法正常使用。
- 点云及其他数据显示混乱。
- 部分功能迁移不完整。
- UI 交互不合理。
- 全屏、最大化、窗口缩放时出现卡顿。
- 多视角编辑自由度不足。
- 无人机轨迹拖影图生成速度慢。
- 长视频编辑及采样帧管理不方便。

本次任务不是简单修复几个 Bug，也不是仅进行 UI 美化，而是全面检查现有仓库，完成架构重构、功能完善、性能优化、实际测试和正式版交付。

软件最终定位：

**完整 RViz 可视化能力 + Final Cut Pro 式视频剪辑能力 + DaVinci Resolve 式时间轴编辑能力 + 无人机科研轨迹图生成工具。**

主要用于无人机科研实验完成后的数据处理、演示视频制作及论文配图生成。

典型使用流程：

1. 无人机实飞时录制 ROS Bag 和外部相机视频。
2. 将 ROS Bag、实飞视频及 .rviz 配置导入软件。
3. 像 RViz 一样自由选择 Topic，显示并编辑各类 ROS 数据。
4. 创建全局视角、TF 跟随视角、正后方跟随视角、高位倾斜鸟瞰视角等。
5. 精确对齐 ROS Bag 与实飞视频的时间戳。
6. 自由添加、移动、缩放多个相机小窗口。
7. 添加文字、图片、速度表及科研实验信息。
8. 通过多轨时间轴编辑各图层的显示时间。
9. 裁剪、拼接实验片段，导出高质量科研演示视频。
10. 从实飞视频生成无人机运动拖影图、飞行轨迹图和论文插图。

最终交付必须是真正能够投入无人机科研实验使用的成熟软件，而不是功能残缺的软件原型。

## 02. 技术架构与 C++ 完整迁移

整个软件统一使用 C++ 和 Qt 开发，彻底摆脱 Python 运行依赖。

### 2.1 技术选型

- UI、数据读取、数据处理、三维渲染、时间同步、视频剪辑、图像处理、轨迹图生成和导出全部采用 C++。
- 检查现有项目的 ROS 版本、Qt 版本、目标运行平台及依赖关系。
- 优先直接复用 RViz 核心库、显示插件、属性系统、渲染引擎和坐标变换能力。
- ROS 1 环境优先评估 librviz。
- ROS 2 环境优先评估 rviz_common、rviz_rendering、rviz_default_plugins。
- 使用 pluginlib 等成熟机制加载兼容的 RViz 插件。
- 使用 tf2 处理坐标变换。
- 使用 rosbag 或 rosbag2 的 C++ API 读取数据。
- 使用 FFmpeg C/C++ API 或成熟的等效方案处理视频。
- 使用 OpenCV、PCL 等成熟库处理图像和点云。
- 充分利用 GPU 加速、多线程、异步任务、增量计算及缓存。

不要自行开发一个功能残缺的简化版 RViz。

不要为了使用纯 C++ 而重复开发成熟库已经具备的功能。

### 2.2 架构原则

建议按照职责划分以下模块，具体实现可根据现有架构调整：

- Application Core：应用核心。
- Project Manager：项目管理。
- ROS Data Engine：ROS 数据读取及订阅。
- Timeline Engine：统一时间轴及时间映射。
- TF Engine：坐标变换及历史状态。
- RViz Integration：RViz 插件及属性集成。
- Render Engine：三维渲染。
- Camera System：多相机及 TF 跟随。
- Canvas Compositor：自由画布及图层合成。
- Video Engine：视频读取、解码及编码。
- Video Editor：多轨视频剪辑。
- Telemetry Engine：速度及实验数据统计。
- Trajectory Studio：轨迹图及无人机拖影图生成。
- Export Engine：视频、图像及数据导出。
- UI Layer：Qt 界面及交互。
- Cache Manager：缓存及资源管理。

模块之间应具有清晰的数据接口，避免严重耦合。

四个主要工作区共享数据服务和项目状态。

### 2.3 线程与资源管理

UI 主线程不得承担耗时的：

- ROS Bag 读取及解析。
- 大规模点云计算。
- 视频解码。
- 无人机前景提取。
- 图像分割。
- 视频编码。
- 文件导出。

遵守 Qt、OGRE、OpenGL 及其他渲染后端的线程安全约束。

不能简单地将所有 GUI 或 GPU 操作移动到后台线程。

合理使用：

- Qt 信号槽。
- 线程池。
- 异步 I/O。
- 有界消息队列。
- 可取消后台任务。
- GPU 资源复用。
- RAII 资源管理。

### 2.4 Python 清理要求

所有原有功能必须完整迁移，不能因语言迁移而减少功能。

迁移完成并验证通过后，再删除：

- 已废弃的 Python 业务代码。
- 无用 Python 文件。
- 不再使用的 Python 运行依赖。
- 废弃模块及冗余资源。

最终软件安装及运行不得依赖 Python 解释器、Python 虚拟环境或 Python 业务处理脚本。

区分应用运行依赖与 ROS 生态可能存在的构建工具依赖，并在文档中明确说明。

保留所有仍有价值的测试代码和测试数据。

整体追求 Apple 软件的精致感、RViz 的专业性和成熟剪辑软件的操作效率。

### 4.2 中文 Tooltip

**Follow Lag（相机跟随滞后）**

控制相机相对于跟随目标的时间滞后效果。

## 06. SLAM 点云与规划地图

支持：

- 拖动片段。
- 裁剪。
- 分割。
- 拼接。
- 删除。
- 复制。
- 轨道排序。
- 轨道隐藏。

- 时间轴吸附。
- 帧级定位。
- 撤销及重做。

### 12.2 每个图层独立显示区间

所有相机小窗口、文字、图片、速度表及其他图层都应拥有独立的显示时间区间。

支持：

- Start Time（开始时间）
- End Time（结束时间）
- Duration（持续时间）
- Trim In（入点裁剪）
- Trim Out（出点裁剪）

例如小窗口 A：

- 1～2 秒显示。
- 2～4 秒隐藏。
- 4～6 秒再次显示。

不得限制一个图层只能存在一个连续显示区间。

区间边界采用统一规则，例如左闭右开，避免重复帧。

### 12.3 时间戳同步正确性

小窗口隐藏期间，实验时间轴仍然继续前进。

例如：

小窗口在第 2 秒隐藏，第 4 秒重新显示时，必须显示实验第 4 秒的实际点云、TF、Odometry、Marker 和轨迹状态。

不得从第 2 秒继续播放。

隐藏的小窗口可以停止不必要的渲染，但必须在重新显示时恢复正确的数据状态。

时间系统应区分：

- Source Time（原始数据时间）
- Experiment Time（实验时间）
- Project Time（项目时间）
- Timeline Time（剪辑时间）
- Clip Local Time（片段局部时间）
- Time Offset（时间偏移）
- Visibility Range（显示区间）

剪辑、重新排列及拼接实验片段后，必须正确建立剪辑时间与实验时间之间的映射。

对于仅修改图层显示区间的操作，不得改变其原有实验时间映射。

ROS Bag、虚拟相机、实飞视频和速度表应保持正确同步。

如果用户主动修改源片段的时间偏移或播放速度，应明确其影响。

保证预览和最终导出结果一致。

## 14. Speed Meter（速度表）及完整实验数据统计

### 14.1 速度数据来源

支持从用户选择的 ROS Topic 读取：

- nav_msgs/Odometry
- geometry_msgs/Twist
- geometry_msgs/TwistStamped
- 其他兼容速度消息。
- 用户选择的自定义速度字段。

自动识别可用速度 Topic，并允许手动选择。

对于包含三轴速度的消息，支持：

- Total Speed（三维速率）
- Horizontal Speed（水平速率）
- Vertical Velocity（垂直速度）
- Velocity X（X 轴速度）
- Velocity Y（Y 轴速度）
- Velocity Z（Z 轴速度）

正确处理速度所属坐标系。

注意 Odometry 中 Pose 和 Twist 可能属于不同坐标系。

需要比较或统计不同方向速度时，应进行正确的 TF 转换。

如果没有直接速度 Topic，允许根据 Pose、Odometry 或 TF 位置进行时间差分估算。

必须明确区分：

- 直接读取的速度。
- 根据位置差分估算的速度。
- 原始速度。
- 滤波速度。

允许用户选择平滑滤波，但不能无提示改变科研统计结果。

### 14.2 实时速度表

支持：

- 数字式速度表。
- 仪表盘式速度表。
- 简洁科研风格速度组件。
- 实时速度曲线。
- 当前速度。
- 最大速度。
- 平均速率。
- 最小速度。
- 飞行距离。

支持 m/s 和 km/h。

速度表可独立修改：

- 位置。
- 大小。
- 字体。
- 字号。
- 小数位数。
- 颜色。
- 背景。
- 不透明度。
- 圆角。
- 显示字段。
- 速度量程。
- UI 刷新频率。
- 显示时间区间。

速度表随实验时间轴准确更新，支持暂停、倒退、快进及随机跳转。

### 14.3 速度统计区间

支持：

- Entire Flight（完整飞行区间）
- Custom Range（自定义统计区间）
- Selected Clip（选定剪辑片段）
- Elapsed Range（截至当前播放时间）

允许用户在速度曲线或时间轴上直接拖动选择统计范围，也支持精确输入起止时间。

统计区间最小编辑步长达到 0.1 s，并支持毫秒级精确输入。

例如，用户选择实验第 10～35 秒，则最大速度、平均速率、最小速度及飞行距离仅根据该区间的有效数据计算。

统计区间可以独立于当前播放时间。

可选支持多个有效统计区间，用于排除起飞前、降落后及无效实验阶段。

### 14.4 统计计算正确性

三维速率按照速度向量的模长计算。

平均速率采用时间加权计算：

平均速率 = 有效统计区间内速率对时间的积分 / 有效统计时长。

对于不规则采样频率，采用合理的数值积分方法，例如梯形积分，并明确边界插值及缺失数据处理规则。

不得简单使用采样值的算术平均值替代时间平均。

区间最大速度基于有效数据样本计算。

明确区分：

- 平均速率。
- 平均速度向量。
- 水平平均速率。
- 垂直速度统计。

速度表默认显示速率大小及其时间平均值。

对于无效数据、缺失时间戳、长时间采样间隔等情况，应提供明确提示，不得随意补齐数据。

飞行距离应明确采用速度积分或位置轨迹累积等计算方式，不能混用不同定义而不说明。

支持导出速度曲线及统计结果，例如 CSV。

### 14.5 高频数据处理

针对 200 Hz 或更高频率的 Odometry：

- 保留原始数据精度。
- UI 刷新与消息频率解耦。
- 不必每收到一条消息就重绘整个 UI。
- 速度曲线允许进行适当显示降采样。
- 最大值及平均值仍基于完整有效数据计算。
- 修改速度表外观不应重新读取 ROS Bag。
- 调整统计区间时快速更新结果。

1. Exclude Drone Frames（仅排除无人机拖影帧）：隐藏无人机图像，保留对应轨迹线。

单帧删除、不透明度修改及手动选帧记录同样需要稳定保存。

## 21. 长视频及轨迹图专项性能优化

必须针对长视频及高密度采样进行专项设计。

例如采用 0.1 s 采样间隔：

- 1 分钟视频约 600 个采样点。
- 10 分钟视频约 6,000 个采样点。
- 30 分钟视频约 18,000 个采样点。
- 60 分钟视频约 36,000 个采样点。

这些规模不能导致 UI 控件数量、完整视频帧缓存或 GPU 资源无上限增长。

### 21.1 核心优化

实现：

- 视频关键帧索引。
- 时间索引。
- 异步视频解码。
- 可见范围内的缩略图加载。
- 轻量化时间轴绘制。
- 有界 LRU 缓存。
- 视频帧缓存。
- 前景提取结果缓存。
- 必要的磁盘缓存。
- 内存及显存预算。
- 增量图像合成。
- 局部属性更新。
- GPU 图层合成。
- 过时任务取消。
- 重复请求合并。

修改透明度、单帧删除、区间排除或轨迹样式时，不得重新执行全部：

- 视频解码。
- 前景提取。
- 图像分割。
- 轨迹计算。
- 完整合成。

修改采样间隔时，尽可能复用已经缓存的采样帧及前景提取结果，只处理新增的必要内容。

### 21.2 实时预览策略

高密度采样可能造成大量无人机图层重叠。

允许提供明确标注的：

- 低分辨率预览。
- 代理预览。
- 渐进式预览。
- 局部更新。
- 后台补全。
- 自适应预览密度。

但不得静默减少用户指定的最终采样数量。

最终导出时恢复用户指定的采样密度及完整画质。

滑块拖动及长视频定位过程中保持 UI 可响应。

## 22. 全屏、窗口缩放及交互流畅度专项优化

之前的软件仅切换一次全屏、最大化或调整窗口大小就可能出现明显卡顿。

必须实际分析原因并优化。

不得仅通过删除动画、降低画质或隐藏功能掩盖问题。

### 22.1 必须优化的场景

- 普通窗口切换全屏。
- 全屏恢复普通窗口。
- 单个预览画面全屏。
- 单个预览画面退出全屏。
- 窗口最大化及恢复。
- 连续拖动窗口边缘。
- 拖动左右侧边栏。
- 调整底部时间轴高度。
- 完整时间轴与迷你时间轴切换。
- 时间轴浮动及重新停靠。
- 属性面板展开与折叠。
- 四个工作区切换。
- 全局视角与 TF 跟随视角切换。
- 单视角与多视角切换。
- 添加、移动和缩放小窗口。
- 拖动文字、图片及速度表。
- 时间轴快速拖动。
- 长视频胶片带快速滚动。
- 不同分辨率显示器切换。
- 不同 DPI 显示器切换。
- 浅色与深色模式切换。

### 22.2 渲染资源生命周期

重点检查：

- 是否在每次 resizeEvent 中重新创建完整场景。
- 是否重复初始化 OGRE 或 OpenGL 上下文。
- 是否重复创建渲染窗口。
- 是否重复创建纹理、Framebuffer 或 RenderTarget。
- 是否重复上传全部点云至 GPU。
- 是否重复加载 ROS Bag。
- 是否重复解析 Topic。
- 是否重复初始化 Displays。
- 是否重复初始化视频解码器。
- 是否存在不必要的 CPU/GPU 同步等待。
- 是否存在渲染资源泄漏。

正常窗口缩放尽可能仅调整：

- Viewport（视口）
- Aspect Ratio（相机宽高比）
- 必要的渲染缓冲区尺寸。
- 必要的 UI 布局。

如果平台机制导致渲染上下文必须重建，应采用最小范围的安全重建机制。

保证场景及项目状态正确恢复。

### 22.3 Resize 与布局优化

采用合理的事件合并、节流及防抖机制。

连续调整窗口大小时：

- 避免每次尺寸变化都触发昂贵的全量重建。
- 合并高频 resize 请求。
- 保持界面响应。
- 正确调整视口。
- 避免重复布局计算。
- 避免全量样式刷新。
- 避免无意义的控件重建。

操作结束后恢复准确的最终渲染分辨率及画质。

防抖不能造成窗口长时间停止更新。

### 22.4 UI 主线程

禁止：

- 同步读取大型 ROS Bag。
- 同步解码大量视频帧。
- 执行耗时点云计算。
- 执行图像分割。
- 执行耗时视频编码。
- 长时间等待后台任务完成。
- 使用频繁 processEvents 掩盖架构问题。

快速连续操作时，过时的计算任务应可以取消，不能阻塞最新请求。

### 22.5 渲染调度

- 避免多个定时器重复触发同一场景渲染。
- 静态场景优先按需更新。
- 动态播放采用合理帧率控制。
- 不可见视角暂停不必要的渲染。
- 多个可见视角共享可复用资源。
- 避免 CPU/GPU 无意义满载。
- 视频解码频率与 UI 刷新频率解耦。
- 渲染队列采用有界管理。
- 保留高频 ROS 数据精度。

实时预览与离线导出使用合理独立的调度方式。

### 22.6 属性动态调整

以下属性变化应尽可能即时反馈：

- 点云颜色。
- 点云大小。
- 不透明度。
- Decay Time。
- 轨迹线宽。
- TF 坐标轴大小。
- 相机距离。
- 相机角度。
- 相机平滑程度。
- 小窗口位置及大小。
- 文字及图片属性。
- 速度表样式。
- 采样间隔。
- 全局及单帧不透明度。
- 排除区间。

只更新必要对象、材质、缓存或渲染属性。

不得因为修改某个 Display 的颜色而重新加载整个项目。

### 22.7 状态保持

窗口及工作区切换时保留：

- ROS 数据。
- Displays 配置。
- 相机位置。
- 相机跟随状态。
- 时间轴位置。
- 图层配置。
- 视频缓存。
- 剪辑状态。
- 轨迹图编辑状态。

从全局视角切换到 TF 跟随视角后再切回来，应恢复此前全局相机位置。

全屏退出后恢复原有布局。

缓存采用合理预算，不能无限增长。
